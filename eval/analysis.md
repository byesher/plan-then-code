# plan-then-code 评测：接口 vs I/O 分模式拆解（结论固化）

> 本文固化最近一轮 bf16 / k=10 baseline 的分模式分析，数据来自：
> `results/report_7B_bf16_k10_20261002_224221.json` 与
> `results/report_14B_bf16_k10_20261002_233830.json`。

## 0. 主要矛盾（一句话先说清）

本项目评测的是模型的**端到端写代码能力**，主指标 = **I/O 题的 pass@1（一次性写对）**；
接口题（给定签名+契约的实现题）**只作参考**。

**大纲（plan-then-code 的中间结构）是 SFT 注入的内部手段，评测端从不要求、也不检查模型是否输出大纲。**
本质是为了让模型写出正确代码的成功率更高，而不是为了逼它输出大纲。

## 1. 评测口径（避免混淆）

- **端到端**：只给自然语言需求 → 模型自由发挥写完整代码 → 检查「编译 + 测试通过」。
- **I/O 题是主评测题**：给需求，模型自己决定结构、自己写完整可运行程序（stdin/stdout）。这是「端到端自由发挥」最纯粹的形式。
- **接口题只作参考**：prompt 里已给出函数签名 + 契约（≈ 一份现成的大纲），测的是「给好大纲后能不能实现」，不是本项目要优化的能力。
- **目标 = 一次性写到位（pass@1）**：一把写对就万事大吉。

## 2. 两种题目模式

| 模式 | 题号 | 给模型的输入 | 评测方式 | 平均样例数 |
|---|---|---|---|---|
| 接口（参考） | p001–p012 | 需求 + 函数/类签名 + 契约 | `import solution` + pytest | 9.2 |
| I/O（主） | p013–p024 | 只给需求 + 输入/输出格式说明 | 跑脚本 stdin/stdout 逐样例比对 | 1.9 |

## 3. 数据（bf16, temperature=0.7, num_samples=10）

### 3.1 分模式 pass@1（主指标）

| 模式 | 7B | 14B | 差 |
|---|---|---|---|
| 接口（参考） | 22.5% (27/120) | 35.0% (42/120) | +12.5pp |
| **I/O（主）** | **51.7%** (62/120) | **50.8%** (61/120) | **−0.9pp（打平）** |

### 3.2 分模式 pass@k（k=10，「至少一次全过」）

| 模式 | 7B | 14B |
|---|---|---|
| 接口 | 50% (6/12) | 83.3% (10/12) |
| I/O | 83.3% (10/12) | 91.7% (11/12) |

### 3.3 0/10（从未全过）题数

| 模式 | 7B | 14B |
|---|---|---|
| 接口 | 6 题 | 2 题 |
| I/O | 2 题 | 1 题 |

## 4. 关键结论

1. **14B 的领先全部来自接口题（+12.5pp）；在 I/O 题上两模型打平（−0.9pp）。**
   合并后的整体 +5.8pp 是「接口领先 + I/O 打平」混出来的，会掩盖真相。以后对比必须分模式报。

2. **I/O 题比接口题容易得多**（pass@1 ~51% vs 22~35%），且每道只有 1~4 个样例（平均 1.9）。
   当前 I/O 题 pass@k 已达 83%~92%，**区分度不足，需要更长/更难的 I/O 题**。

3. **「模块税」**：同一道题从「脚本版(I/O)」改成「模块版(接口)」后，7B 掉 29pp（51.7%→22.5%），
   14B 只掉 16pp（50.8%→35.0%）。7B 在脚本形态下已与 14B 打平，其短板集中在「多函数模块结构」这一维——
   这正是 plan-then-code SFT 要补的。

4. **在主指标（I/O 端到端一次性写对）上，7B 与 14B 持平**。因此选型不再受「哪个更强」约束：
   **两个都做 SFT，做横向对比**（已全面转向 A100，成本可承受）。

## 5. 需要诚实标注的混淆

I/O 版通过率高，有一部分来自「样例少」（1~4 个，接口题 6~13 个），不全是「脚本比模块简单」。
所以 §4 第 3 条「模块税 29pp vs 16pp」的绝对值不能全归因于「结构难度」；
但「两模型在 I/O 打平、在接口拉开 12.5pp」这个**差值**是干净的——说明两模型真正的能力差在「多函数模块结构」这一维。

## 6. 后续方向

- **7B 与 14B 都做 SFT**，产出 plan-then-code 微调版，做 `baseline → SFT` 的横向对比，主指标都用 **I/O 题 pass@1**。
- **扩题库**：找 I/O 格式、带「题目 + 评测样例」、代码长度 ≥ 当前 I/O 题（参考实现 24~79 行）的公开数据集，
  跑一轮评估，确定「代码长度落到哪一档最合适」（当前 I/O 通过率太高，需加长/加难）。
- **红线**：训练数据绝不包含这 24 道评测题。
